# Castle ribbon axis packet census at `9550e397`

One headless native Chromium case captured the actual Float64 input and output words passed to the existing castle ribbon WASM solver at overview, operational, and close camera presets. It passed in 4.212 seconds (the case body took 3.503 seconds) with the original 60-second case and 300-second global limits. The page reported an NVIDIA RTX 5070 Ti through ANGLE/Vulkan, and the test asserted a real WebGL context rather than a software renderer. The selected game state, command log, and map resource diagnostics were identical before and after the three captures.

The runtime was the 1,648-file `9550e397568ff448689bc5904ec0651b04bfe717` source with exactly two temporary instrumentation overlays: `src/ui/map/wasmCastleRibbonPlanner.ts` at SHA-256 `83683d74cc2fa474478619927b48e26d3c1c7b4e79fcae63aa3e6e9ad14579f0`, and `e2e/castle-axis-packet.spec.ts` at `8af3f4b4268e585fbe5181077c52484291784593f1dc7e832a5c31933c1aad25`. The before proof matched the original source and all 29 pinned dependency targets; the after proof matched those same inputs except the two named overlays. The overlays did not enter production source. The instrumented planner read the actual WASM arena with `DataView.getBigUint64`, preserving each Float64 word bit for bit from input start through `outputStart`, then from `outputStart` to the output end. Individual packet fields contain numeric words, status, and work; they do not add JS candidate IDs or flags to the WASM input. The outer evidence also retains game state, commands, and layout diagnostics for the no-mutation check.

For close view, each of 64 candidates considers the same 168 fixed rectangles and 63 other candidate rectangles, giving `64 × (168 + 63) = 14,784` reserved scans per axis before locality rejection. The 1,451 and 2,001 endpoint counts are survivors of the recorded ±48-pixel axis test, not a proposed production implementation or measured speedup. The complete 2,321,543-byte packet JSON is retained twice, with identical SHA-256 `288f9951c0f817dc11dd7c208bd2079fa5c1a5195b46b01a3119b400a56642dc`; `verify.py` decodes the bits and recomputes these counts.

An offline Node control invoked the same WASM export using each recorded packet, copied input bytes, and compared output bytes on every call. After 50 warmups, five batches of 100 calls produced median full-call costs of 0.003889 ms (overview), 1.657859 ms (operational), and 2.828659 ms (close). This includes input copying and output comparison and runs outside the browser frame; it is not a live post-WASM stage measurement, an FPS result, or an upper bound on frame cost. The first control invocation failed because the WASM import object lacked `env`; its exact TypeError and exit 1 are retained. The corrected control supplied only the required import and passed with exact output comparison. The separate `castle-close-profile-9550e39` package measures a different, later stage.
