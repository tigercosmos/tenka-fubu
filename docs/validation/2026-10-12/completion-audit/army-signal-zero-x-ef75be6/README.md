# Army-signal zero-X optimization, exact geometry and bounded performance evidence

The change in `ef75be660e0a142da9c6130ac04ffefc9820e7fb` skips the Y-axis overlap arithmetic only when the original X-axis span is exactly zero and one invocation-wide bound proves that the skipped arithmetic is finite. Otherwise it uses the original overlap expression. Proposal order, scores, and the 1,000,001-work cutoff remain unchanged. The source comparison is against `9550e397568ff448689bc5904ec0651b04bfe717`; the candidate browser runtime was that exact base plus the one production-file overlay whose SHA-256 matches the adopted commit. This is not a claim that the entire `ef75be6` tree ran in those browser jobs.

The copied original implementation has SHA-256 `c59493b5…79295b`; the adopted implementation has SHA-256 `6271e113…e160c4c0`. Differential tests cover sparse and dense layouts, finite extremes around `MAX_VALUE/16`, signed zero, subnormals, and sparse obstacle arrays. An instrumented copy of the original and the adopted function both charged **1,000,001** work units on the dense fixture and produced the same ordered output hash `4a5bed53…8c5065`. The focused 11 unit tests, type check, touched ESLint, and formatting check passed. The original `forEach` validation semantics, including sparse arrays, were retained.

On the same isolated Linux RTX 5070 Ti/Vulkan runtime, the original and one-file candidate produced byte-identical full published-view JSON (15,575,980 bytes, SHA-256 `aa64ea9e…e796c3`) for nine day 0–2 × three-camera observations. The observer includes all signals and the other published map geometry, canonical and command hashes, resources, and GPU identity. Its only exclusions were the four previously established nonvisual counters. Both geometry jobs passed. The first baseline observer attempt failed an erroneous diagnostic zero-tick guard: the intended day progression creates two ticks. Its raw failure is retained separately; the corrected observer was byte-identical across the two successful jobs.

The **unchanged original 30-second strict 60-FPS close-view case still failed** on the candidate: 34.131850 FPS, slow-frame FPS 28.5714, p95 35 ms, 120 mounted armies and 56 minimum visible. The clean-base counterpart in [`castle-close-profile-9550e39`](../castle-close-profile-9550e39/) measured 33.236739 FPS, slow-frame FPS 27.7778, p95 36 ms. The paired FPS difference is +0.8951 (+2.69%), one observation per source. The candidate test stopped at the FPS assertion; its later original assertions did not execute. Raw posthoc measurements and the separate profile do not turn those unexecuted assertions into passes. The original strict-60 gate remains RED.

The separate, nonacceptance 10-second CPU profiles showed the mapped army-signal solver at 1.359065 s / 328 frames (4.144 ms/frame) for the clean base and 1.210925 s / 342 frames (3.541 ms/frame) for the candidate, a 14.6% per-frame reduction in that stage. The surrounding signal stage was 4.832 → 4.276 ms/frame (11.5%). Both profiles retained equal before/after core state, command log, and resource counts within each run. Profile sampling and frame counts differ; these are indicative source-stage observations, not an isolated solver-call timing or a 60-FPS result.

All offline whole-function benchmark rows are retained, including contradictory early regimes. The 20-pair runs after four warmups measured dense cost **+5.9%** and **+8.0%**; one crowded run measured candidate 2.95× slower while another measured it faster. After seeing those unstable timings, we ran an additional 40-pair comparison after 60 warmups: sparse −10.9%, crowded −9.3%, dense **+7.6%**. The longer warmup was chosen _after_ inspecting earlier rows. Abrupt timing-regime changes are consistent with compiler tiering, but no compiler trace proves that cause. This optimization is a limited incremental gain for the measured native close view with a disclosed dense synthetic regression; it does not close the performance gate.
