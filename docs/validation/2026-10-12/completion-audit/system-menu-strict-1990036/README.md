# System menu owner under React StrictMode

The DEV visual-map fixture exposed a real SystemMenu ownership bug. Its gear click reached the handler and promoted `systemMenu`, but the modal disappeared 3.3 ms later. The production entry point wraps `App` in React `StrictMode`; `SystemMenu` previously closed its owned modal during layout-effect cleanup, which StrictMode replays on initial mount. A real `SystemMenuHost` unit control passed without StrictMode and failed with it (1 pass, 1 failure). The ordinary four-step new-game settings path also passed on the original source, so that path alone did not expose the DEV replay.

The adopted change delays only the owned-modal release until a microtask. Cleanup still immediately unsubscribes and revokes callbacks; an effect generation prevents the replay cleanup from releasing an owner reclaimed by the next setup. The release retains exact modal-object and game-identity checks and `resume:false`. Commits `6cb9643614cb8b50bca78912c223199a2f621404` and `199003680ab269a6129610216790788884f8aa9f` contain the production fix and final test. The first test-only commit `84c527e` was amended: its detached-button assertion did not exercise a retained callback. The final test captures the actual `ConfirmDialog.onConfirm` prop through a pass-through wrapper, invokes it after owner replacement, and verifies that it cannot submit the stale title action or dismiss the replacement.
